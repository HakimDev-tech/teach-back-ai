# Database foundations — Phase A

## Tables
- `profiles`: one minimal application profile per `auth.users` identity.
- `organizations`: tenant boundary.
- `organization_memberships`: professional user-to-organization relationship.

Patient identity is not a professional membership role. No clinical-domain tables are created in this phase.

## Relationships
One Auth user has one profile. An organization has many memberships; a profile can have memberships in multiple organizations. A unique constraint prevents duplicate membership for the same organization/user pair.

## Constraints and indexes
Names and slugs are length/format constrained. Roles are owner/admin/clinician; statuses are active/suspended/revoked. Authorization lookup indexes cover user/status/organization and organization/status/role. Timestamps are timestamptz generated by PostgreSQL.

## Provisioning and ownership
An AFTER INSERT trigger provisions a bounded display-name profile from untrusted Auth metadata. Organization creation is performed by `create_organization(name, slug)`, which atomically creates the first owner. Ownership transfer uses `transfer_organization_ownership(org_id, target_user_id)`; the target is promoted before the current owner is demoted. A trigger protects the last active owner.

## Migrations and types
Migrations are immutable ordered SQL files under `supabase/migrations`. Apply from a clean local database with `supabase db reset`. Generate types from the live local schema using `npm run db:types`; never hand-edit generated output.

A generated type file and npm lockfile require package installation and a running local Supabase stack. They are not represented as verified or committed in this remote-only execution environment; generate and commit them from a provisioned development environment.
